# v7 計畫 —— 從「會動的機器」到「別人能用的完成品」

> 制定日期 2026-08-12。**這份取代 `plan_v6_一台機器.md`**(v6 的 R0–R5 已全部完成並上線)。
>
> 目標一句話:**別人拿到這個 repo,能在網頁上把一家銀行的財報核對完、看到分析,
> 而且不需要問你任何問題。**
>
> 範圍**刻意收窄**(2026-08-12 使用者裁示):只做銀行財報。「通用性」= 多幾家銀行、
> 未來的期別 —— **不是**換任意題目。這一條收窄推翻了 v6 R3 的方向,理由見 §0.3。

## 零、體檢 —— 以下每一條都是 2026-08-12 實跑量到的

### 0.1 核心三層是好的,而且比 v6 文件描述的更好

| 層 | 狀態 | 證據 |
|---|---|---|
| 抽取 | ✅ 不綁銀行 | `v4/reader.py` 走 `claude -p`,prompt 裡零銀行名 |
| 分桶 / 口徑 / 閘門 | ✅ 不綁銀行 | `buckets.py` 提到銀行名 41 處,**37 處是註解裡的證據引用**(「這條同義詞是哪份文件證實的」),4 處是行尾註解;判斷邏輯零耦合 |
| 資料模型 | ✅ 三張表 | `facts.db` 68 docs / 1673 observations / 64 rulings;人工永遠蓋過機器,有並行寫入保護 |
| 人審介面 | ✅ 真的能用 | 實際開起來核對過:左列右圖、桶名就地可改、錨值即時對照 |

**這一節的用途是防止做錯:v7 不重寫抽取、分桶、驗證、資料模型。**

### 0.2 doc id 已經人看得懂(2026-08-12 完成)

`202504_5847_AI3` → `202504_玉山_個體`。解析從**六處各寫一次**(`core/report.py` 還是
位置式切片 `doc[7:11]`)收成 `docid.py` 一份;`config.BANKS` 從**四份副本**收成一份。

驗收做過:四張發布表逐格比對**零變動**,唯一差異是 `_build` 裡的來源指紋
(檔名改了指紋本來就該變)。

### 0.3 ⚠️ v6 R3 的「視覺化脫鉤」解錯了問題 —— 這是這份計畫最重要的一條

v6 花了 2–3 天做 `viz_generic.py`(通用視覺化層,不認得任何銀行名字),
驗收判準是「換一份 `schema.yaml`(例如上市公司研發費用)照樣畫得出來」。

**但使用者要的通用性是「多幾家銀行」,不是「換題目」。** 於是:

- `viz_generic.py` **162 行,零樣式、零互動、裸 HTML 表格** —— 技術上通用,
  產品上沒有臉,而且**沒有任何人會用它**(`/generic.html` 是「試畫」連結)。
- 它解決的是使用者沒有的問題,卻沒有解決使用者有的問題。

**而且「make_web.py 焊死這個題目」這個診斷本身已經過期。** 實測:

```
make_web.py:14   BANKS = D["banks"]           ← 讀 data.json,不是寫死
make_web.py:937  re.sub("const BANKHUE={...}", 由 config.BANK_COLORS 注入)
make_web.py:939  re.sub("const VC={...}",      由 config.BANK_COLORS 注入)
```

寫在 JS 字串裡的五家色票是**佔位符,產出時被正則換成設定值**。
v6 文件說的「BANKHUE 五家色票寫在 JS 字串裡」是看原始碼得到的結論,
**沒有看產出**。

**結論:通用視覺化層(162 行)應該退場,不是把它做漂亮。**
維持它要付的代價是第三條渲染路徑 + 一份假 schema 的回歸測試,
換到的是一個沒人用的功能。

### 0.4 加第 6 家銀行,實際會壞在哪 —— 比想像中窄很多

活程式碼(排除 `archive/` `legacy/` `scratchpad/` `test_`)裡寫死五家清單的地方
**只剩一處**:

```
yields.py:43   ORDER = ["中信", "兆豐", "國泰", "富邦", "玉山"]
```

它往下傳到 `sim/state.BANKS` → `sim/axes.py:242` 的 `config.BANK_COLORS[b]`
(直接索引、**無 fallback**,缺色票會 KeyError)。

其餘路徑都已經是設定驅動的:上傳 PDF → 封面判個體/合併 → 抽取 → 分桶 → 發布 → 畫圖,
全程不需要知道是哪一家。**華南(5838)、第一(5844)已經在 `config.BANKS` 裡,
它們的 2025 年報就躺在 `pdf_cache/`,零筆已抄。**

> 這一條的意思是:「加銀行」這件事**離可用只差一點**,不是要重構。
> v7 應該把這一點補完並且證明它 —— 而不是為了想像中的通用性再蓋一層。

### 0.5 三條渲染路徑 —— 這才是真正的重複

| 檔案 | 行數 | 做什麼 | 誰用 |
|---|---|---|---|
| `make_web.py` | 941 | 公開儀表板:跨行比較、時間趨勢、估值視角、獲利視角 | CI → GitHub Pages |
| `web/workbench.js` | 1394 | 核對台:網格、逐格核對、桶名編輯、裁示 | 本機工作台 |
| `web/sim.js` | 823 | 配置模擬器 | 本機工作台 |
| `viz_generic.py` | 162 | 裸表格 | **沒有人** |

四份加起來 3320 行,**同一份資料被畫了四次,四套各自的渲染邏輯**。
「矩陣/網格」在其中至少出現三次、「時間序列」兩次、「缺漏標示」三次
(而且三處的視覺語言不一致)。

這跟這個 repo 反覆出過的病是同一個形狀(memory: `two-implementations-one-rule`),
只是這次長在渲染層。

### 0.6 完成品的門檻:別人拿到之後的前三分鐘

現在 clone 下來的人會遇到:

- `python3 app.py` 起得來(✅ 實測過),但**看到的是你的資料**。
  沒有「這是示範資料 / 我要放自己的」這條路的指引。
- 想加自己的銀行 → **沒有任何 UI 或文件講怎麼做**。
  要自己去改 `config.BANKS`(而且要知道有這個檔)。
- `run_tests.py` **7 支紅燈**(30/37)。給別人的東西不該是紅的,
  而且其中至少一支是真的分歧(見 0.7)。

### 0.7 7 支失敗測試,不是同一種東西

| 測試 | 第一個錯誤 | 判讀 |
|---|---|---|
| `test_gap` | `module 'fill' has no attribute '_taxonomy_gap'` | **死 API** —— 測試指著已不存在的函式 |
| `test_ingest_equiv` | `KeyError: 'AC'` | 同上類,資料形狀變了 |
| `test_decide_equiv` | `29/2190 rows differ` | ⚠️ **真的分歧** —— `decide()` 與 `buckets.bucket()` 兩個實作對 29 列給出不同的桶 |
| `test_b3` / `test_b5` | 硬編基準數字 | 過期基準(`facts/` 長大了) |
| `test_derive` | `推導後直接通過 = 0` | 註解說已被 revalidate 取代 |
| `test_jobs` | 指紋快取 | 待查 |

**`test_decide_equiv` 那 29 列要先查。** 它正是「一道規則兩個實作」的活體,
而且它管的是分桶 —— 分錯桶會生出假的浮虧(memory: `wide-cost-bucket-alignment`)。

### 0.8 資料涵蓋率(供參考,v7 不以此為目標)

個體網格 **34/70 格有資料(48%)**;2023 起 **23/40**。
使用者已明講不要逐個修資料,所以這個數字在 v7 是**呈現問題**不是**填補目標**:
缺的格子要讓人一眼看出「這裡沒有資料、原因是什麼」,而不是看起來像壞掉。

## 一、如果今天從零開始蓋,會蓋成什麼樣

> 這一節刻意不參考現有結構,先想對的形狀,再去對照差多少。

### 1.1 它其實是一個「有審核流程的資料集編輯器」

不是「報表產生器」。核心迴圈是:

```
一份 PDF  →  機器讀出候選數字  →  人看著原始頁確認  →  確認過的進事實庫  →  重算分析
                    ↑                                        ↓
                    └────────── 對不上就退回、標明為什麼 ──────┘
```

**這個迴圈已經完整存在而且會動。** 從零蓋也會蓋成這樣。

### 1.2 一個前端,三個面向,共用一套元件

從零蓋不會寫四份渲染邏輯。會先做一套元件:

| 元件 | 三個面向怎麼用它 |
|---|---|
| **網格**(期別 × 銀行,含完整度著色) | 核對台:點進去核對 · 分析頁:唯讀總覽 |
| **逐桶表**(分類 × 桶 × 口徑) | 核對台:就地改桶 · 分析頁:唯讀明細 |
| **時間序列** | 分析頁:趨勢 · 模擬器:情境軌跡 |
| **缺漏標示** | 三處共用同一套視覺語言(現在三套) |

差別只在**互動能力**(可編輯 vs 唯讀),不在渲染。

### 1.3 「加一家銀行」是一條有 UI 的路徑,不是改設定檔

從零蓋會把它做成:網頁上輸入代碼與名字 → 上傳(或抓)PDF → 自動跑完 → 出現在網格上。
**現在缺的只有第一步**(其餘都會動)。

### 1.4 設定的邊界:銀行清單是資料,不是程式碼

`config.BANKS` 現在是 Python 字典 —— 改它要編輯原始碼。
從零蓋會讓它是一張表(或 `banks.yaml`),網頁能改。

### 1.5 不會蓋的:題目無關的通用層

從零蓋、知道目標是銀行財報,**不會蓋 `viz_generic.py`**。
把銀行清單/期別/桶當資料傳進去,已經足夠應付「多幾家銀行、未來期別」。

## 二、鐵律

v6 的九條全部沿用(不放寬檢查、不打版型、不手塞同義詞、不補 0、衍生物不落地、
人工蓋過機器、不長第二條路徑、一次一條 session、「兩種原因一種結果」是 bug)。

v7 新增三條,對應 §0.3 / §0.5 / §0.6:

10. **不為想像中的需求蓋抽象。** 通用層、外掛機制、schema 驅動 —— 除非**現在就有
    第二個真實使用者**,否則不蓋。v6 R3 花 2–3 天蓋了一個沒人用的通用層,
    這條就是為它寫的。
11. **同一種視覺元素不准有第二套實作。** 網格/時間序列/缺漏標示各只准一份。
    新面向要用,就去用那一份;不合用就改那一份。
12. **給別人的東西不准是紅的。** 測試全綠才叫完成品。修不動的測試要嘛修、
    要嘛刪掉並寫明為什麼 —— **不准留著當背景雜訊**,那會讓真的紅燈看不見。

## 七、順序的理由

**R0 在最前面**,因為 `test_decide_equiv` 是唯一可能牽出資料正確性問題的紅燈,
而它管的是分桶。若它是真 bug,R1 的「逐格相同」比對會建立在錯的基準上。

**R1 在 R2 前面**,因為 R2-3(網頁上加銀行)要顯示在網格上 ——
先做 R2 會對著一個要被換掉的渲染層寫。

**R4 最後**,因為分發方式取決於前面做出來的東西長什麼樣。

### 如果只有一天

**R0 全部 + R2-1。** 讓測試全綠,並修掉唯一一處寫死的五家清單。
做完之後「加一家銀行」在資料層與分析層都通了,只差網頁上的入口。
