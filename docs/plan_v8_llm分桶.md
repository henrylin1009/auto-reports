## 零、體檢 —— 為什麼要做這件事

### 0.1 那段給 LLM 的 prompt,從來沒送給任何 LLM

`config.BUCKET_RULES` 是一段 636 字、寫給模型看的分桶指示
(開頭就是「把每列歸到下列其一(**用會計意義判,不是字面**)」)。

實際的資料流是:

```
config.BUCKET_RULES(636 字,寫給 LLM 的散文)
        ↓  人手抄成關鍵字表(rules.py:26「逐字抄自 BUCKET_RULES,不得自行擴充」)
   rules.propose()      子字串比對
        ↓
   buckets.bucket()     86 條**精確比對**查表    ← 認不得就丟人審佇列
```

**那段散文被人工翻譯成關鍵字表,再退化成精確比對。**
「用會計意義判,不是字面」這句話,被實作成了純字面比對。

### 0.2 長尾的大小 —— 這是成本的分母

各家「查表認不得」的不重複科目名(實測全庫 facts/):

| 銀行 | 認不得的名字數 |
|---|---|
| 第一 | 13 |
| 華南 | 6 |
| 玉山 | 4 |
| 富邦 | 2 |
| 中信 | 1 |
| **全庫不重複** | **23** |

新銀行明顯比舊銀行多(第一 13、華南 6 vs 中信 1)—— 因為舊銀行的名字
早就被人一條一條加進查表了。**這就是「每加一家銀行要人工分桶 N 次」的來源。**

### 0.3 查表永遠追不上的那類名字

現在人審佇列裡真正要人判的 7 個(現行 doc id 格式):

```
票券投資 · 買入定期存單 · 債券 · 按攤銷後成本衡量之債務工具投資
權益工具投資 · 債務工具投資 · 政府機構不動產抵押證券
```

其中「政府機構不動產抵押證券」= agency MBS → 資產基礎、「權益工具投資」→ 股票、
「票券投資」→ 貨幣市場,**用會計意義判都很直接**,但精確比對永遠命不中,
除非有人手動把每一種寫法都加進 86 條表裡。

而「債券」「債務工具投資」則是**真的需要看上下文**才判得出來(可能是公債/
公司債/金融債)—— 這種本來就該留給人,LLM 也該誠實說不知道。

### 0.4 你要的架構已經蓋好 85%

| 需求 | 現況 | 位置 |
|---|---|---|
| 人工改**數字**(改/加/刪列) | ✅ 已接到 UI,`why` 必填,每列蓋 `_src` | `webdata.edit_row()` + `/api/row` |
| 人工改**分桶** | ✅ 拖曳 UI,可選「只改這幾列」或「立成全域規則」 | `webdata.rebucket()` + `/api/rebucket` |
| 人工核可 / 撤銷整格 | ✅ | `ratify()` / `revoke()` |
| 稽核軌跡 | ✅ `_src` + `git diff facts/` + Decision 三態 | — |
| **LLM 分桶提案** | ❌ **唯一缺口** | — |

前端 12 個 API 端點全部接得到,人工編輯面是完整的(實測:改列/加列/刪列
三個呼叫點都在,刪列還會要求填理由才送出)。

### 0.5 接縫是設計時就留好的 —— 這是這份計畫成本低的原因

```python
core/decisions.py:232   def decide(row, group, rules_by_name, propose_fn)
core/ingest.py:95       decide(..., rules_mod.propose)      ← 全庫唯一呼叫點
```

`propose_fn` 是**注入參數**,而且只有一個呼叫點。換提案者不必動結構。

**而且鐵則 2 讓這件事天然安全**:`core/decisions.py:243` 明訂
「decide() 不得憑機器推論產生 CONFIRMED」。所以 LLM 提案**必定**落在
`PROVISIONAL` → 自動進 `review/queue.jsonl` → 人 ratify 才變 CONFIRMED。
**稽核鏈一行都不用改。**

### 0.6 ⚠️ 不准用 `core/llm.py`

`core/llm.py` 是 Gemini 的出口,它的檔頭自己寫著:

> 抄列的預設抽取器改成 `claude -p`,`fill_auto.read_gemini` 已刪除。
> 理由是 gemini 生過 PDF 裡不存在的字(`公允僵值`、`有僵證券`)

實測佐證:人審佇列裡 34 個舊格式殘留名字中,有一整批是
`政府公僵`、`公司僵`、`裟生金融資產`、`金融資產評僷調整` —— 全部來自
舊 doc id(`202502_5836_AI3`),正是 gemini 時期的污染。

**v8 一律走 `fill_auto.read_claude`(`claude -p`,用使用者自己的訂閱、
不需 API key)**,與現行抄列同一條路。

### 0.7 人工核可現在擋住什麼 —— 這一節決定 v8 的形狀

**「歸檔」本來就不需要人工核可。** FILED 出口(v7 已上線)就是
「算術過了就寫進 `facts/`,分類未定也照寫」。人工核可擋的是**發布**:

```python
core/publish_gate.py   publishable = arithmetic_ok and fully_confirmed
```

實測(2026-08-12,全庫 198 格):

| | 格數 |
|---|---|
| 已歸檔 archived | 198 |
| 可發布 publishable | 114 |
| **算術全過、只差人工核可分桶** | **69** |
| 算術本身沒過(跟核可無關) | 15 |

**69 格資料都在、算術都對,只因為分桶沒被人一條條按過就發不出去。**

使用者裁示:**這個閘門要拿掉。** LLM 分好就算數,人要抽查再抽查。

#### 這個裁示改變的風險邊界(要寫清楚,因為是使用者在承擔)

**被包住的**:分桶錯**只會把錢在桶之間搬,不會憑空生出或吃掉錢** ——
三段恆等式(`sum(wide 7 桶) + 衍生 + 評價調整 == 類別合計`)仍然逐格驗證。
所以最壞情況是「公司債被算成金融債」,不是總額錯。

**沒被包住的**:分桶錯位**確實會生出假的浮虧**
(memory `wide-cost-bucket-alignment`:帳面/成本兩邊分桶錯位,分券種相減
就會算出假數字,富邦 2022H2 曾算成 −11.41%、真值 −2.15%)。
**這是這個裁示要換到「不卡住」所付的代價,不是零成本。**

**所以 v8 的做法不是「拿掉檢查」,是「把閘門換成標示」**:
資料照發,但**每一格、每一列都看得出來分類是誰下的**,而且要能一鍵抽查。

## 一、目標架構 —— 三層,確定性優先

```
① 查表   buckets.SYN(86 條,每條都人工確認過)   ← 命中就結束,不問 LLM
              ↓ 查不到
② LLM 分類  claude -p,回「桶 + 理由」或 __UNKNOWN__  ← 只處理長尾
              ↓ 有桶就算數:歸檔 ✓、發布 ✓、同時進「待抽查」清單
③ 人抽查   同意 / 改桶 / 改數字 / 判 UNCLASSIFIED   ← 隨時可做,不擋前面
```

**② 與 ③ 之間沒有閘門** —— 這是使用者裁示的核心(§0.7)。
人工核可從「解鎖的動作」變成「提升信心度的動作」。

**唯一仍然會擋發布的是 `UNCLASSIFIED`(連桶都給不出來)** ——
那不是「還沒人看」,是「這一列到底算什麼沒有答案」,
三段恆等式會因為它兜不攏(未知列不落進任何 wide 桶),
本來就會被算術那一關擋下,不需要另外一道人工閘門。

**為什麼保留查表而不是全部交給 LLM**:

1. **可重現性**。同一份財報重跑兩次,結果必須逐位元組相同
   (`build.py --diff` 連跑兩次輸出相同,是這個工具現有的保證)。
   已確認的 86 條是確定性的;LLM 不是。
2. **成本與速度**。實測全庫長尾只有 23 個不重複名字,絕大多數列都命中查表。
3. **人已經付出過的判斷不該重問**。那 86 條是人一條條核可過的,
   每次重跑都丟給 LLM 再問一次,等於把人的裁示丟掉。

## 二、鐵律

v7 的十二條全部沿用。v8 新增三條:

13. **LLM 分好就算數,但永遠標明是誰分的。**(2026-08-12 使用者裁示改寫)

    原本這條寫的是「LLM 只提案不定案」,那是初稿的誤解。使用者要的是
    **不卡住**:LLM 分好就能歸檔、能發布,人事後抽查。

    但**「不擋」不等於「看不出來」**。這條的實質要求變成:
    任何一格、任何一列,都要能回答「這個桶是查表命中、LLM 分的、
    還是人親手改的」。**分不出來就是違反這條** —— 那才是真正不可逆的損失
    (資料錯了可以改,但「不知道哪些沒被看過」就沒辦法抽查)。

    ⚠️ **這條與 `core/decisions.py:243` 的鐵則 2 直接衝突**
    (「decide() 不得憑機器推論產生 CONFIRMED」)。處置見 R1-1:
    **不是刪掉鐵則 2,而是把 CONFIRMED 的語意還原成它本來該有的意思
    ——「人親自確認過」**,同時讓**發布不再要求 CONFIRMED**。
    機器仍然不准自稱 CONFIRMED,只是 CONFIRMED 不再是發布的門票。
14. **LLM 不准猜。** 判不準要回 `__UNKNOWN__`。`config.BUCKET_RULES` 自己
    就已經這樣寫了(「判不準 → 不要猜、不要丟進『其他』」),只是從來沒有
    真的送給模型過。**「其他」是表上真的印著『其他』的科目,不是收容所。**
15. **LLM 提案必須附證據且標明來源。** Decision 的 `references` 要記
    `kind="llm"` + 模型講的理由 + 模型版本。人審時看得到「它為什麼這樣提」,
    而不是一個沒來由的桶名。**混在 `kind="rule"` 裡就分不出哪些是機器猜的。**

### R2 抽查介面 —— 閘門拿掉之後,這一層就是唯一的品質防線(1.5 天)

**閘門一拿掉,「看得見」就從方便變成必要。** 資料會直接發出去,
所以使用者必須能隨時回答「哪些是機器分的、我還沒看過」。

| # | 做什麼 | 驗收 |
|---|---|---|
| R2-1 | 每一列顯示分類來源:**查表命中 / LLM 分的 / 人改的**,三種視覺可分辨(不是只有文字差異) | 隨便點開一格,一眼看得出哪幾列沒被人看過 |
| R2-2 | **「待抽查」清單**:所有「LLM 分的、還沒人看過」的列,可依銀行/期別/桶篩選 | 這是取代原本「人審佇列」的東西 —— 佇列語意從「**擋著等你處理**」變成「**建議你看一下**」 |
| R2-3 | 一鍵「我看過了,沒問題」→ 升 CONFIRMED;「改成別的桶」→ 走既有 `rebucket` | 兩條路都留 `why`;**人否決 LLM 時要把原始提案一起記進稽核**(哪些它會分錯,是下一輪改 prompt 的依據) |
| R2-4 | 每一列能**看到證據頁**(這個名字出現在哪一份、哪一頁) | 分桶檢視已有 `showEvidence()`,接上即可,不要另寫一份 |
| R2-5 | 分析頁/公開儀表板標明「本頁含 N 列機器分類、未經人工複核」 | 別人看到數字時知道它的成色 —— 這是拿掉閘門之後對外的誠實義務 |

> **R2-5 不是裝飾。** 閘門在的時候,「發布出來的東西都被人看過」是隱含承諾;
> 拿掉之後那個承諾不成立了,**畫面上就必須講出來**,否則等於默默降低了

## 五、明確不做

- **不動人工編輯面。** 改數字/改桶/核可/撤銷都已經能用(§0.4),v8 不重寫。
- **不拿掉查表。** 它是可重現性的來源(§一)。
- **不讓 LLM 自稱 CONFIRMED。** 鐵則 2 保留 —— 但 CONFIRMED 不再是發布門票(R1)。
- **不用 Gemini。**(§0.6)
- **不碰算術那一關。** 六道檢查、錨值核對、三段恆等式**全部原封不動**。
  拿掉的是「人工核可分桶」這一道,**不是**算術驗證。
  **v8 只碰分類,不碰數字。**
- **不做「LLM 自動修正數字」。** 數字有錨值可以驗證,那一層不該讓模型介入。

## 六、風險

| 風險 | 目前證據 | 處置 |
|---|---|---|
| **拿掉閘門後,錯的分桶會直接發布** | 分桶錯位確實會生假浮虧(memory `wide-cost-bucket-alignment`,富邦 2022H2 −11.41% vs 真值 −2.15%) | **這是使用者明確承擔的取捨**(§0.7)。緩解:三段恆等式仍逐格驗證(錯桶只搬錢不生錢)、R2 全套抽查介面、R2-5 對外標明成色。**不假裝這個風險不存在** |
| 「看得見」做不好 → 沒人知道哪些沒被看過 | 閘門拿掉後這是唯一防線 | 鐵律 13 改寫成「可以不擋,但分不出來就是違反」;R2-1/R2-2 是硬需求不是加分項 |
| LLM 分類品質不如預期 | 未知 —— 這正是 R0-4 要量的 | R0-4 不設門檻先量;真的不好就**只做 R1**(解 69 格)、不接 LLM |
| 組合提案器改動到既有查表路徑 | 94 格既有 Decision 是基準 | R1-1 逐筆比對,任何一筆變動都算回歸 |
| 每次重跑結果不同,破壞可重現性 | 查表優先的設計就是為此 | 只有**新名字**會問 LLM;人 ratify 之後就進查表,之後不再問 |
| 模型幻覺出不存在的桶名 | gemini 生過 PDF 裡不存在的字(§0.6) | R0-3 白名單驗證 + 注入測試 |
| 「其他」桶被當成收容所 | `BUCKET_RULES` 已明文禁止 | 鐵律 14;R0-4 的評測要特別看有幾個被丟進「其他」 |

## 七、順序的理由

**R0 在最前面而且不接上**,因為「LLM 提案夠不夠好」是這整份計畫的前提。
先花 1 天量清楚,比接上去之後才發現它常常提錯、然後回頭拆掉便宜。

**R1 的回歸驗收(94 格 Decision 逐筆不變)排在接上去的當下**,不是最後 ——
一旦既有資料的分類被動到,後面所有比較都建立在錯的基準上。

**R3 挑沒調校過的銀行**,理由見該節。

### 如果只有一天

**做 R1,不做 R0。**(初稿寫的是「做 R0」,使用者裁示後改了。)

理由:R1 **不需要 LLM** 就能解除 69 格 —— 那些格子的桶其實早就有了
(查表或關鍵字命中),純粹卡在「還沒有人按過確認」。拿掉閘門是
**投報率最高、而且立刻看得到**的一刀。

LLM 補長尾(R0)是第二步 —— 它處理的是那 23 個查表認不得的名字,
影響面比 69 格小得多。
