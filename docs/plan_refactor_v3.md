## 1. 診斷摘要(為什麼要改,附實測數據)

執行者請先自己重跑一次下方「§7 現況量測指令」確認以下數字仍成立,再開始動工。

### D1:驗證閘門已退化成恆真

系統中共有 **9 條接受路徑**:雙錨全過 / 無外錨靠 internal / 錨不可靠+自洽 / note 源自動 self_ok / best_effort / rescan 二次機會 / 吞列指紋事後救援 / 面板救援 / 手改 JSON。

實測:**186/186 全過,0 fail。** 一個從不拒絕的閘門不帶資訊。歷史軌跡是「每次假性失敗就加一條救援」,而非修錨。

### D2:容差寬到不可能偵測實際發生的錯誤,而且它幾乎沒在工作

| 量測 | 值 |
|---|---|
| 對帳精確相等 | **180 / 186 (97%)** |
| 容差寬度(`max(5000, 1%)`) | 3.3 億 ~ **109.7 億** |
| 靠容差救回來的格 | **2 格**(差 8.0 億、4.7 億) |
| 真的對不上的格 | 4 格(全部是手改 `_accept_note`) |

證人抓到的真實錯誤是「兆豐 OCI 可轉讓定存單:明細 85.7 億 vs 主附註 153.97 億」,差 68 億 —— **小於容差上限**。所以總額對帳在數學上不可能偵測到實際會發生的分桶錯誤。而財報本來就精確加平,那 2 格被吞掉的差正是最該人看的。

### D3:唯一沒有自我驗證的讀,被當成真理

`cross_ok = _tie(recon_fair, bs_anchor)` 比的是「LLM 讀的明細表」對「LLM 讀的 BS 三列」—— 同模型、同模態、同失效分布。兩者不合時沒有原則性方法判斷誰錯,所以長出五個代理猜測機制:`locate_bs` 的 reliable 旗標、`check_bs_anchors`、`reconcile` 的 anchor_doubt 分支、事後吞列指紋(而且它用 `recons[other]` —— 一個本身未驗證的量)、面板 ±40% 帶。

**通用規則其實已經有了,只是沒用在 BS 上:「全列相加 == 印出合計」。** 資產負債表恰好最容易自證(資產側整欄 == 資產總計)。

### D4:路由用檔名,而事實在文件裡

`is_halfyear`(檔名期別碼)決定走明細表或主附註,緊接著 `if kind == "AI1": half = True` 特例。這個特例本身證明路由鍵挑錯 —— 真正決定來源的是「這份文件、這一類有沒有明細表」,而且是 per-(文件,類別) 而非 per-文件。

附帶的靜默錯誤:`extract_v2.PERIOD` 收 01/03(季報)判為半年報,但 `bridge_v2.doc_period` 是 `per=="02" → H1,其餘 → H2`。一份 AI3 季報掉進 `pdf_cache` 會被標成 H2,**覆蓋掉年報那格,全程無警告**。

### D5:唯一守著「實際發布維度」的檢查被關掉了

pass/fail 單位是 (文件, 類別),但網站畫的是 (期別, 銀行, 類別, **桶**)。總額對帳對分桶免疫。逐桶證人 186 格中 28 格示警(15%),被判「太吵」(基礎口徑錯配,約 25/36 是假警報),`bridge_v2` 明文不讓它上網。→ **圖表上的桶拆分實質無驗證。**

證人吵的根因與 D4 同源:主附註 Trading/OCI 印成本、明細表印公允。這個知識散在四處(退役的 `schema.MEASURE`、證人的 `col = "值" if cls=="AC" else "成本"`、`extract_from_note` 的 `cost=None`、`bridge_v2` 註解)。

### D6:所有 fallback 都在降低標準,沒有一條在提升能力

有意義的退路:換 key、睡 15 秒重試、擴頁、關鍵字重掃。
無意義的退路(只是放寬接受):弱錨採信、錨可疑採信、面板救援、手改 JSON。

全系統只有一個模型 `gemini-3.5-flash-lite`。當失敗來自能力不足(掃描圖/字元湯/折行)時,**沒有任何路徑能增加能力**。而「夠用」的判準是 186/186 —— 那個由設計保證恆真的數字。自我封閉迴路。

**連動:容差之所以必須存在,是因為沒有 escalation。有了 escalation 就能要求精確相等。**

### D7:results.json 兼四職,產生非冪等棘輪

`panel_validate` 取鄰期中位時只收 `_pass=True` 的鄰居,而救援會把 `_pass` 設 True 並**寫回同一個檔**。第二次跑,第一次救回的格變成合法鄰居,救援範圍單向擴張。

且 4 格 `_accept_note`(人真的去看 PDF 確認 BS 是掃描誤讀,最有價值的資訊)**程式碼裡沒有任何地方寫它** —— 是一次性腳本手灌進衍生檔案,沒進版控。因配額限制無法全量重跑,所以也不敢刪那個檔。

### D8:泛用性已有反證

引擎那半段(digest+LLM 定位、影像讀值、schema 驅動輸出)確實與目標無關。但驗證層焊死在三類金融資產:`_LOC_SCHEMA` 直接 `required: Trading/OCI/AC`、`_BSALL_*` 硬寫、`CLASSES` 全域。

**最強反證是 `phase0.py`** —— 第二個目標出現時是用 regex 另寫一條管線,引擎沒有吸收它。

## 2. 目標架構

核心主張:**把「對帳」從一堆兩兩比較,升級成「宣告式恆等式」;並要求每一個讀都自證。**

現在散落各處的比較其實是同一種東西:

| 現有分支 | 其實是 |
|---|---|
| `internal_ok`:逐列相加 == 印出合計 | 恆等式 |
| `cross_ok`:對帳總額 == BS[類別] | 恆等式 |
| `check_bs_anchors`:三類和 ≤ 資產總計 | 恆等式(弱版) |
| 逐桶證人:明細桶 == 主附註桶 | 恆等式(逐桶) |
| `_selfok` / 吞列指紋 / 面板帶 | 上述的代理猜測 |

```
targets.yaml         ← 宣告:定位 prompt、讀值 schema、(類別,來源)→基礎欄位、必須成立的恆等式
   │
   ├ 1 INDEX    pages_text + digest(便宜,一次)
   ├ 2 LOCATE   一次 LLM → 所有目標(含 BS)的候選頁集合
   ├ 3 READ     逐候選影像讀 → Read{rows, printed_total, basis, source, pages, verified}
   │              ★ 每個讀都自證:sum(rows) == printed_total(BS 也一樣:資產側整欄 == 資產總計)
   ├ 4 SOLVE    在「已自證」的讀之間評估宣告的恆等式,挑滿足最多恆等式的指派
   │              (取代 is_halfyear 路由、AI1 特例、select_detail 挑/湊、reliable 旗標)
   ├ 5 DECIDE   全部恆等式成立(精確)→ 收
   │            不成立 → 升級能力(大模型/高解析/擴頁)重讀一次
   │            仍不成立 → 拒收,不發布,進複核佇列  ← 真正的 fail-loud
   └ 6 PUBLISH  只發布收下的;資料集以 (prompt+model 版本) 為鍵,不可變
   │
overrides.yaml       ← 人工判斷,進版控、可 review,程式只讀不寫
   ↓
bridge → data.json → site
   ↓
panel 離群 → 監控報表(只提示,永不翻轉 accept/reject)
```

**性質:1 條接受規則、1 條升級規則、1 條拒收規則。** 9 條接受路徑收成 1 條。

**該砍**:`locate_bs` 的 reliable 旗標、`check_bs_anchors`、`reconcile` 的 anchor_doubt 分支、`extract_all` 尾端吞列指紋迴圈、`panel_validate` 的救援那半、`is_halfyear` 路由 + AI1 特例、`extract_from_note` 的獨立 reconcile 路徑。

**該留**:`locate_by_digest`(好設計)、影像讀值、「全列 == 印出合計」(那條通用規則)、用錨在候選間挑選、逐桶證人(修好基礎後才有用)、fail-loud(要真的能觸發)。

##### 模板漏了一個欄位:`adj`(調整項)

原模板的自檢恆等式是 `sum(buckets) + deriv == total`。人工填寫時發現 10 份裡**有 4 份不成立**,原因是財報常有既不入桶、也不是衍生的列:

- 減:備抵損失(國泰 AC −120,378、富邦 AC −604,359、中信合併 AC −90,604)
- 金融資產評價調整(中信合併 Trading +809,475、OCI −73,672)

已加 `adj` 欄位,自檢改為 **`sum(buckets) + deriv + adj == total`**。

⚠ 這件事本身就是 P5 的證據:「衍生」不足以描述非桶列,恆等式必須把調整項當成一等公民。P5 的宣告式 targets 要用同一條恆等式,不要再長出第三個特例欄位。

##### 人工填寫時實際踩到的坑(P5 設計時要看)

這五類錯誤是**人**在抄的時候犯的,而 LLM 犯的是同一批錯 —— 這說明它們不是「模型不夠聰明」,是**表格結構本身有歧義**,規則層必須明確處理:

1. **多金額欄**:兆豐明細表同時有「取得成本」與「公允價值/總額」欄,AC 表則是「總額 / 備抵損失 / 未攤銷溢折價 / 帳面金額」四欄。抄錯欄 → 整表偏移。**規則:對帳要對得上印出的合計,自然會選中正確欄。**
2. **小計線**:小計以上才分桶,以下的衍生段整段不入桶。衍生段裡也有一列叫「其他」,與桶名撞名(這正是那個 472.6 億 live bug 的成因)。
3. **同義詞**:短期票券/商業本票/國庫券 → 貨幣市場;央行定期存單/可轉讓定期存單/銀行定存單 → 可轉讓定存單。

### P1 — 一切讀值自我驗證,證據依「可驗證性」排序

**投入產出比最高的一步。** 要加的是「讀取者能自己決定看哪裡、能再看一次」加上「欄位加總自證」;那五個猜測機制不必逐一拆解,**換掉讀取架構之後它們會失去存在理由**(見 P1.0b 實測)。唯一必須另外寫的新東西是**拒收路徑**(P1.4b)—— 因為這條管線至今從未拒收過任何東西。

#### P1.0 為什麼:證據階層是反的(P0 實測)

P0 抓到 4 格 BS 錨誤讀,全在掃描圖 PDF:

| 文件 | 真值 | BS 讀到 | 形狀 |
|---|---|---|---|
| 202104_5836 Trading | 98,053,708 | 214,961,937 | 抓到別表/別期 |
| 202202_5836 Trading | 122,605,853 | 222,312,645 | 同上 |
| 202202_5836 OCI | 130,852,278 | 236,202,422 | 同上 |
| 202102_5841 Trading | 126,299,850 | 361,492,785 | ≈ Trading+OCI,抓到合計列 |

**這不是 OCR 把 8 看成 3,是抓到別的數字。** 掃描圖沒有文字層 → `locate_bs` 定位失敗 → 現行做法是把第 1–15 頁**整包當影像**餵給模型叫它猜。15 頁裡有個體 BS、合併 BS、兩三個期別欄,抓錯是必然的;而抓錯了**沒有任何機制會發現**。

根本問題在於兩個東西的性質不同:

- **BS 錨是一個孤立的數字。** 沒有任何算術能驗證它。讀錯了跟讀對了長得一模一樣。
- **附註是一整欄。** 各列相加必須等於印出小計,再加衍生與調整項必須等於印出總計。讀錯了**算術會爆掉**。

附註**本質上比 BS 可驗證**,系統卻讓不可驗證的去推翻可驗證的。這 4 格全部是這樣壞的:附註讀得完全正確(P0 已逐列人工核過,兩道算術自洽),卻被一個沒人驗證過的 BS 數字判為「有疑慮」,於是系統長出五套機制去猜該信誰。

> **那五套機制存在的唯一理由,就是因為沒人去驗證那個錨。**

#### P1.0b 2026-07-25 實測:應該換架構,而不是逐一拆機制

P1.0 診斷正確,但開藥方開輕了。當天做了三個實驗,結論是**那五個機制不用一個個拆,換掉讀取架構它們會自己消失**。

**實驗一:定位 —— 一個能自己決定看哪頁的讀取者,4/4 全對。**

不給頁碼提示,只給 PDF 和「找哪一類的 BS 金額」:

| 文件 | 黃金集 | v2 讀到 | agent 讀到 |
|---|---|---|---|
| 202104_5836 Trading | 98,053,708 | 214,961,937 | ✅ |
| 202202_5836 Trading | 122,605,853 | 222,312,645 | ✅ |
| 202202_5836 OCI | 130,852,278 | 236,202,422 | ✅ |
| 202102_5841 Trading | 126,299,850 | 361,492,785 | ✅ |

過程本身就是證據:發現文字層是 CID 亂碼 → 讀目錄拿到「個體資產負債表 8」→ 推 PDF index 7 → 渲染後**發現數字欄在裁切範圍外 → 改範圍再看一次**。

第三步是關鍵。現行管線在那裡只會回傳它看到的東西 —— 那正是 214,961,937 的來源。**不是模型笨,是它沒有「再看一次」的權限。**

**實驗二:結構 —— 也是能力問題。** 富邦 Trading「其他」應為 6,419,339,v2 讀成 53,682,185 = 47,262,846(衍生小計)+ 6,419,339。它把兩個區段揉在一起了,而表上 `小計` 兩行明確劃分了區段。

**實驗三:分桶 —— 不是能力問題,換模型無效。** 兆豐 OCI 有「銀行定存單 5,691,891」與「定期存單-可轉讓 6,668,555」。黃金集兩列都算「可轉讓定存單」,v2 把前者丟進貨幣市場。**光看那張表,兩種分法都講得通** —— 這是你家的分類約定沒寫下來,再強的模型也只是換一種猜法。

##### 14 個 bug 的完整分類

| 類型 | 格數 | 例子 | 解法 |
|---|---|---|---|
| **定位錯** | 4 | 掃描圖 BS 抓到小計列 | **agent 迴圈**(P1) |
| **結構讀錯** | 5 | 衍生小計混入「其他」、併列錯位 | **agent 迴圈**(P1) |
| **定義沒定** | 5 | 銀行定存單歸哪桶、取總額還是帳面金額 | **規則表**(P3) |

> **9 格是能力問題,5 格是定義問題。兩邊不能互相取代,少做任何一邊都會留下一半的錯。**

那 5 格的共通點是**恆等式管不到的維度**:分錯桶、或整欄一致地換一種口徑,`sum(桶)+衍生+調整 == 總額` **兩種都會平**,自動檢查永遠分不出來。所以必須有人宣告 —— 這是 P3 的規則表非做不可的理由,不是為了方便。

##### 連帶決策:換模型 →(2026-07-26 已被取代,見 §6c 決策 1)

`gemini-3.5-flash-lite` 撐不住這個迴圈 —— 它做不到「這頁是小計列,我換一頁」。而**閉合迴圈配弱模型比開迴路更危險**:終止條件會退化成「數字終於湊上了」,長出一個比現在更安靜的猜測分支(違反 §0.1 第 3 條,只是這次不是人手寫的)。

架構和模型要一起換,只換一邊會失敗,而且兩種失敗方式不同:

- 只換模型 → 定位權還在 Python 手上,它只是**把小計列讀得更準**,4 格一格都不會好
- 只換架構 → 弱模型不會反駁「你給錯頁了」,只會把答案往能對上的方向挪

上面這段推論仍然成立,但結論不再是「改 `config.py:MODEL` 換成 `claude-opus-4-8`」。**2026-07-26 拍板:整條讀值路徑不再呼叫任何 API,由 Claude Code 直接執行(§6c 決策 1)。** 因此 `MODEL` / `MIN_GAP` / `.env` / 金鑰輪替一併刪除,而不是換值。

當時量的成本數字保留當背景(黃金集 10 份 1770 頁中 **1709 頁(97%)文字層可用**;BS 頁 `scale=2` 裁切後 **235 token 即清晰可辨**,當天手動用的 `scale=8` 是 42,756 token,浪費 180 倍)—— 第二個數字在 P1 仍然有用,它決定了看圖時該用多大的 scale。

##### 文字層有三種,不是兩種 —— OCR 的最危險

擴到全部 89 份時抓到第三類:**OCR 產生的文字層**。它 grep 得到、看起來正常,但數字會被靜默截斷:

```

`\d{1,3}(?:,\d{3})+` 會只吃到 `32,776` 就停,**回一個小三個數量級的值而且不會報錯**。這比回 `None` 危險得多 —— 正是 §9「標記 ≠ 拒收」的同型錯誤:一個看起來被正常處理過的錯值。

修法是**截斷偵測**:完整的千分位數字後面不可能再接數字或逗號,接了就代表被切斷 → 整份退給視覺路徑。

守衛沒有弄壞任何一個原本正確的讀。**要嘛確定對,要嘛沉默** —— 這是 `bs_anchor.py` 的驗收標準,不是「涵蓋率越高越好」。

#### P1.1 動作:一切讀值必須自我驗證

不要問模型「FVTPL 是多少」,要它**讀整欄**。

   - 代價:定位失敗時最多 15 次呼叫而非 1 次。只發生在文字層定位失敗的少數文件,可接受。

欄位加總過(必要條件,不過就直接拒收)
  ├ 比較欄對得上上期真值        → 表鎖對了
  │   ├ BS 欄位加總過且相符      → 收,雙來源,最高信心
  │   ├ BS 讀不出來/未自證       → 收,標記單來源
  │   └ BS 已自證但不相符        → 真衝突 → 升級(P2)
  └ 比較欄對不上 / 無上期可比    → 升級(P2) → 人工佇列
```

P0 那 4 格會落在第二列:附註自洽、BS 未自證 → **正確收下**,而那個錯的 BS 數字被拒絕,**連進來吵架的資格都沒有**。

#### P1.3 比較欄:定位校準,不是數值佐證

每張附註都印兩到三期。2022H1 的附註印了 2021-12-31,應精確等於 2021 年報的數字。

⚠ **講清楚它能做什麼、不能做什麼**(這點原稿寫過頭,已修正):

- 它**不能**驗證當期數字。當期永遠是新的。
- 它驗的是**有沒有鎖對表**。定位錯誤有個關鍵性質:**同時汙染整張表的每一欄**。模型若鎖到合併報表,當期與比較期**都會**是合併數字。
- 所以它是**強否定、弱肯定**:
  - 比較欄對不上已知上期真值 → 當期讀值**一定不可信**(來自同一張表)
  - 比較欄對得上 → 表鎖對了、列對應對了;當期**尚未被驗證**,但最常見的那類錯誤已排除

它免費(同一次讀值就拿到)、精確(不是 ±40% 啟發式),且**精準打中 P0 實際觀察到的唯一失敗模式**(4 格全是定位錯)。

**覆蓋範圍**:資料橫跨 2021–2025 約 10 期。

- 舊的 9 期(~135 格):下一份報表的比較欄會回頭驗它。遲來,但會來。
- **最新 1 期(~15 格):沒有任何東西能驗。** 這是設計上承認的缺口,不是漏洞。前緣格子一律走 P2 升級 → 兩次獨立讀值一致才收 → 不一致進人工佇列。一年兩次、每次十幾格,可負擔。
- 明年這 15 格會被下一份報表的比較欄回溯驗證。若屆時發現當初收錯,代表升級策略不夠強,回頭調。

**副作用**:這條精確等式取代 `batch_v2.panel_validate` 的 ±40% 中位數棘輪 —— 那個機制不但是啟發式,還會把 fail 改寫成 pass 並回寫同一個檔案(見 D7)。

#### P1.4 刪除清單

換架構之後這些會自然失去理由,逐項確認刪乾淨即可(不是先刪它們、再想辦法補洞):

- `locate_bs` 的 `reliable` 回傳值,與所有下游 `bs_reliable` 參數傳遞
- `check_bs_anchors` 整個函式
- `reconcile` 裡的 `anchor_doubt` 分支(`if not cross_ok and self_ok and not bs_reliable`)
- `extract_all` 尾端的「吞列指紋事後救援」迴圈
- `batch_v2.panel_validate` 的**救援寫回**(面板降為唯讀監控,見 P4)
- `config.py`:`TOL = 0`、`TOL_REL = 0`。保留常數當旋鈕但預設為 0;`_tie` 改精確比較後 `_tol` 只剩一個呼叫點,一併簡化

未自證的 BS **不得當錨**:該類 `bs_anchor = None` → 走「無外錨」路徑。P2 之前先讓它直接拒收(覆蓋率會暫時掉,是預期的)。

#### P1.4b 拒收路徑(缺這條,前面全部白做)

**現況:管線從來沒有拒收過任何東西。** 誠實率 30/30 是假的 —— 所有格子都收下,黃金集也沒有一格判 `unreadable`。P1 若不補上這條,`__UNKNOWN__` 和「欄位加總不平」都沒有地方去。

##### 一、桶名沒有驗證

`extract_v2.py:397`:

```python
nsub[s["bucket"]] = nsub.get(s["bucket"], 0) + s["amount"]
```

`bucket` 是自由字串。模型回傳 `__UNKNOWN__`(P3 規則表要求判不準時填這個)會**安靜地變成第 10 個桶**,照樣被算進 `bucket_sum`,恆等式照樣平,然後在 `bridge_v2` 被丟掉 —— 一句話都不會說。

- 桶名不在 `config.BUCKETS` 裡 → **錯誤**,不得默默新增
- 出現 `__UNKNOWN__` → 整欄拒收,進審查佇列

##### 二、拒收單位是「一份文件的一個類別」

不是單一桶。恆等式的單位就是那一欄;某列名目不認得時,它的金額真實存在,你不知道它該去哪。**只丟掉那一桶,會讓其他桶看起來很完整,而那是假的。**

##### 三、`null` 與 `review` 是兩種狀態,不准並存

| 狀態 | 前端行為 | 觸發 |
|---|---|---|
| **`null`(拒收)** | 走勢圖**斷線**、表格灰色「—」 | 恆等式不平 / `__UNKNOWN__` / 重讀次數用盡 |
| **`review`(存疑但採用)** | 值照畫,加待複核標記 | 跨期離群等**外部**訊號 |

**前端不用改,兩者都已實作**:`make_web.py:97`(`null` → 「—」)、`make_web.py:347`(`if(v==null){pen=false;return;}` → 斷線)。`data.json.wide` 現有 70 格中已有 20 格是 `null`,機制在跑。

要改的是**接線**。現行生產環境的 review 旗標:

```
2021H1|中信 Trading:
  「BS錨為掃描影像誤讀…實讀值經時間序列連續性與表內自洽驗證正確,
    採信為弱錨待複核」
```

診斷完全正確 —— 它自己都寫了「掃描影像誤讀」(正是 P1.0b 實驗一那 4 格)。錯的是後半句**「採信」**。結果是兩者最糟的組合:使用者看到一個待複核標記,**而圖上畫的是錯的數字**。

> **標記 ≠ 拒收。中間那個位置不存在 —— 要嘛信這個數字,要嘛不信。**

`bridge_v2.py` 的 `_needs_review` 來源改為:

- 刪掉「弱錨 / 錨可疑」(那是 P1.4 要刪的機制)
- 改接「恆等式不平 / `__UNKNOWN__` / 重讀用盡」→ 輸出 **`null`**,不是值 + 標記
- `review` 保留給跨期離群(現有 `面板離群`,P4 降為唯讀監控)

##### 四、迴圈終止條件(最容易寫歪的一段)

「對不上就重讀」若終止於「數字終於平了」,就是一台湊答案機。三條硬性要求:

1. 重讀必須取得**新證據**(換頁、換區域),不得原地改口
2. 有**次數上限**,到頂即拒收
3. 改答案要**說得出理由**,理由要能對照原文

##### 五、實務上洞不會很多

穩態每季只新增 5 份。拒收進佇列 → 看一眼、把新名目加進規則表 → 重跑,通常發布前就處理完。**網站上長期留著的 `null`,只會是文件本身就殘缺的少數格 —— 那種本來就該是洞。**

#### P1.5 驗收

以 P0 基準線為準:

| 指標 | 基準 | P1 要求 |
|---|---|---|
| 逐桶正確率 ★ | 86/96 (90%) | **不得下降** |
| 誠實率 ★ | 30/30 (100%) | **不得下降** |
| 錨正確率 | 26/30 (87%) | 應上升至 30/30,或那 4 格轉為「無錨」 |
| 總額正確率 | 30/30 (100%) | 可下降(拒收變多),但每一格下降都要能說出原因 |

- 那 4 格 BS 錨誤讀,預期變成「正確讀出」或「拒收」。**兩者都可接受,靜默通過不可接受。**(P1.0b 實測顯示 4/4 可正確讀出。)
- 逐桶那 10 個錯:**結構類 5 格**(衍生小計混入、併列錯位)P1 應一併修好;**定義類 5 格**留給 P3,P1 不該動到。分類見 P1.0b。
- **誠實率的意義會在 P1 之後才成立** —— 現在的 30/30 是「全部收下」的產物。P1 後若出現拒收,總額正確率會下降而誠實率應維持,那是正確的形狀。

**風險**:整欄讀 + agent 迴圈使呼叫次數與 token 上升,且離開免費層。實測全量 $14 / 每季 $0.80(P1.0b),可接受。

**回滾**:`git revert` 該 commit;`extract_v2_results.json` 不要覆蓋,先寫到 `extract_v2_results.v3.json`。

### P2 — 能力階梯(escalation)取代降低門檻

**為什麼**:見 D6。P1 之後會有一批格子拒收,其中多數是能力問題(掃描圖/字元湯),需要的是「讀得更用力」而非「降低標準」。

**動作**

1. `config.py` 加模型階梯:
   ```python
   MODEL_LADDER = ["gemini-3.5-flash-lite", "gemini-3.5-flash", "<付費較強模型>"]
   ```
2. `_gen` 之上加一層 `read_with_escalation(read_fn, verify_fn)`:
   - 第 1 層:`MODEL_LADDER[0]`,原樣讀
   - 恆等式不成立 → 第 2 層:升模型 / 提高影像解析度 / 擴頁,重讀
   - 仍不成立 → **拒收**,寫入複核佇列
   - **同層同 prompt 不重讀**(temperature=0 無新資訊,只燒配額;現有程式碼已正確做到這點,維持)
3. 升級只在恆等式不成立時觸發,預期命中率 3~5%。
4. 複核佇列輸出到 `review_queue.json`:`{檔名, 類別, 失敗的恆等式, 讀到什麼, 錨是什麼, 相關頁碼}`,一份能讓人直接開 PDF 核對的清單。

**關於成本(使用者已拍板,2026-07-25:採用混合式)**

✅ **已核准**:第一輪一律用免費模型;**只有恆等式不成立的格子才升級付費模型**。以 3~5% 命中率計,一年成本約幾分錢。

執行者必須遵守的邊界:
- 付費模型**只能出現在階梯的最後一層**,不得當第一層、不得用於定位(定位是純文字 digest,免費層綽綽有餘)。
- 每次升級付費呼叫都要記錄到 `review_queue.json`,欄位含 `escalated_to`(用了哪個模型)與 `cost_estimate`,讓花費可稽核。
- 加一個上限保險絲:單次批次的付費呼叫數超過 `MAX_PAID_CALLS`(建議預設 20)→ 停止升級、剩下的直接拒收並記錄。避免某次 prompt 改壞導致大量格子失敗、無聲燒錢。
- **不得整批改用付費模型**。若某次批次付費呼叫超過總格數的 15%,那是管線退化的訊號,應該停下來查,而不是繼續花錢硬過。

**驗收**:`score_golden.py` 的正確率相對 P1 回升,且誠實率不下降。`review_queue.json` 內容應該是「人看了會同意確實有問題」的格子。

## 9. 一句話總結(給執行者的判斷準則)

> 這套系統的問題不是不夠聰明,是**在一個未經驗證的錨上疊了太多層信任仲裁**,然後用一個恆真的指標確認自己沒問題。
> 把錨修成可自證的,上面那層就不必存在了。
> **證據要依「可不可驗證」排序,不是依「來自哪張表」排序。** 一整欄有算術可查,一個孤立數字沒有 —— 所以附註贏過 BS,不論 BS 看起來多權威。
> **任何讓你想「再加一條規則來處理這個特例」的時刻,先問:是不是因為某個讀沒有自證?**
>
> ——— 2026-07-25 實測後補 ———
>
> **迴圈沒閉合,就只能在原地猜。** 讀值一次就走、對帳結果永遠回不到眼睛,那五個猜測機制不是設計失誤,是開迴路的必然產物。給讀取者「再看一次」的權限,它們自動失去理由。
> **但閉合迴圈配弱模型比開迴路更糟** —— 終止條件會退化成「數字終於湊上了」。架構和模型要一起換。
> **恆等式抓得到漏列、讀錯欄、讀錯表,抓不到分錯桶** —— 因為總和照樣平。桶是唯一沒有自動保護的維度,所以分桶規則必須是**宣告的資料**,不是猜的結果。
> **標記 ≠ 拒收。** 「知道可能有問題但還是用了」是最壞的一種,比直接用還壞 —— 它讓錯誤看起來像是被處理過了。
>
> ——— 2026-07-26 實測後補 ———
>
> **先問「這件事需要判斷嗎」,再問「哪個模型做得到」。** BS 錨看起來非 LLM 不可,實際上三行規則 + 一組主管機關統一的科目代碼就 126/126。分桶看起來要懂會計,實際上是一張 40–60 列的查表。**每從 LLM 手上收回一個維度,就少一個恆等式管不到的錯誤來源。**
> **不要比對會斷行的東西。** 中文標籤 112/126,科目代碼 126/126。差別不在聰明,在**選了一個不會被排版破壞的識別子**。
> **沒驗證過的偵測器,和沒驗證過的 grep 錨,是同一個錯誤。** 寫完一個 heuristic 就採信它的輸出,跟管線用一條從沒對過答案的規則去定位,性質相同 —— 差別只在有沒有回頭打開那一頁看。
> **「難」和「壞」要分開算。** 文件本身的性質(中文沒有 Unicode 對照表)換誰讀都難;程式沒去翻第 38 頁只是 bug。混在一起就會高估工作量、也會錯過那個一行就能修的。
