## 一、目標架構

> **三張表 · 四個純函數 · 四個狀態 · 一個入口 · 設定驅動的視覺化。**

### 1.1 資料模型:三張表,一個 SQLite 檔

| 表 | 一列是什麼 | 誰寫 | 性質 |
|---|---|---|---|
| `documents` | 一份 PDF:來源、sha256、頁數、取得時間 | 取得層 | append-only |
| `observations` | 「某文件某頁某列的一個數字」+ 原始列名 + 抽取者 + 時間 | 機器 | **append-only** |
| `rulings` | 人的裁示(改值 / 改桶 / 標無資料)+ 理由 + 誰 + 何時 | 人 | **append-only,永遠蓋過機器** |

**其餘一切都是這三張表的純函數,不落地成狀態:**
桶、寬表、verdict、待辦佇列、覆蓋率、`data.json` —— 全部隨時可以重算。

用 SQLite 不是為了效能,是為了**交易與並行寫入**(見 0.3 最後一行:
兩個 session 同時改 68 個 JSON,誰贏看時序)。
**JSON 匯出保留**,當 git 版控的快照與人可讀的 diff —— 那是它現在真正的價值,
不是當資料庫用。

### 1.2 管線:四個純函數,每一步的輸入輸出都是資料

```
ingest(pdf)                 → observations   ← 唯一碰 LLM 的地方
classify(observations)      → buckets        ← 純查表 + 同義詞,零 LLM
verify(buckets)             → verdict        ← 純算術,三道恆等式
publish(verdict, rulings)   → data.json      ← 純函數
```

現在 `fill.py` / `v4.reader` / `adapter` / `results` / `build` **每一支都做這四件事的一部分**,
所以「換一個抽取器」等於重寫半條管線。分乾淨之後,加第二個抽取器只是換 `ingest` 的實作。

### 1.3 狀態機:四格 + 一個正交旗標

```
未抽 ──► 已抽待驗 ──┬──► 綠(算術證明成立)
                    └──► 要人看(證不了)
                                    ⊗ 人已裁示  ← 正交,蓋過上面任何一格
```

現在是 `done·todo·blocked·rejected·no_data·na` 六種 ＋ `GREEN·RED·GREY·RATIFIED` 四種,
十種畫在同一張表上。

### 1.4 視覺化:吃設定,不吃程式碼

一份 `schema.yaml` 描述:實體(銀行)、期別、維度(分類 × 桶)、口徑、恆等式。

- **通用層** —— 任何 schema 都畫得出來:矩陣、逐桶表、時間序列、缺漏標示、
  每格點下去看得到出處(哪份文件、第幾頁、誰抽的、人有沒有改過)
- **題目層** —— AC/OCI 配置、殖利率、模擬器,當外掛掛上去

**驗收判準一句話:換一份 `schema.yaml`(例如「上市公司研發費用」),通用層要照樣畫得出來。**

### 1.5 入口:一個

```
python app.py  →  瀏覽器自動開  →  拖 PDF 進去  →  看進度  →  核對  →  按發布
```

現有 26 個 `__main__` 全部收成它的子命令,不是平行入口。

## 二、鐵律(違反就是做錯,不是風格問題)

沿用的四條 —— 這四條是這個系統唯一的資產,一條都不准鬆:

1. **不准為了讓某格通過而放寬檢查。** 拒收是正確輸出。
2. **不准針對某一家銀行 / 某一個版型寫規則**,包含魔術常數(容差、視窗、門檻)。
3. **不准手工往 `buckets.SYN` 塞名字** —— 塞錯了沒有任何檢查抓得到。
4. **不准補 0。** 缺欄 = 未揭露 ≠ 0。取不到就是 `null`。

v6 新增的三條,直接對應 0.2 / 0.3 的病:

5. **衍生物不准落地成狀態。** 桶、寬表、verdict、待辦一律現算。
   要快取就標明是快取,而且刪掉之後系統照樣正確。
6. **人的裁示永遠蓋過機器,而且永不被無聲覆蓋。** `rulings` append-only。
7. **不准長第二條路徑。** 新功能若需要「再寫一個 ratify / 再開一個目錄 / 再加一條 build 分支」,
   那就是模型不對,停下來改模型,不要加分支。
8. **一次只跑一條 session,直到 R1-5(並行保護)做完。** 現在的儲存是 68 個 JSON 檔,
   兩個 process 同時寫同一格,誰贏看時序,而且沒有任何東西會告訴你發生過。
   今天已經發生過一次(「兩件事撞在一起了,我讓兩個 job 寫同一個檔」)。
9. **「兩種原因,一種結果」就是 bug。** 查無 / 對不上 / 讀不到 塌成同一個可觀察狀態,
   閘門就會在你看不見的地方變成恆假或恆真。0.3b 那件事的根就是這個,
   而修完之後它在上一層又長了一次(R0-0a)。**每次寫「回 None」之前先問:None 有幾種意思?**

## 七、順序的理由

**R0-0 在最前面**,理由只有一個:**它已經開始了。** 工作區有 26 個檔在改動中,
動的還是 `facts.py` / `transcribe.py` / `core/closure.py` 這種底層,而測試一支沒跑。
在它 commit 之前,後面每一項要量的基準都是浮動的 —— 0.2 那組 41/11 就是這樣被作廢的。
**沒收完的重構比沒開始的重構貴。**

**R0 接在後面**不是因為最有價值,是因為它正在製造要清的東西:
網頁上那顆按鈕的預設仍然是 gemini,而 gemini 已經證明會生出 PDF 裡沒有的字。

**R1 在 R2 前面**,因為「PDF 拖進來之後寫到哪」這個問題,在沒有 `documents` 表的時候
只能回答成「寫進 `pdf_cache/` 並遵守 `resolve.py` 的檔名慣例」—— 那是第十個存狀態的地方。
**這是唯一我願意接受換順序的地方**:如果需要先看到「別人的 PDF 進得來」這件事發生,
可以先做一個吃現有檔名慣例的簡版 R2(約 1 天),但要在 R1 完成時把它改掉,
而且要在那時候真的改,不要留成第十一個地方。

**R3 在 R2 後面**,因為通用層要畫的「缺漏標示」「點下去看出處」都是讀 R1 的三張表;
先做視覺化會對著一個要被換掉的資料形狀寫。
