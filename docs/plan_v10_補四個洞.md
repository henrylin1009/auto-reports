## 洞① `④合計==錨` 不認得「兩個口徑」— 5 格假警報

**症狀**(華南 202504 OCI,使用者截圖):

```
④合計==錨(整格拼樹):p138:印出合計 378,456,348 在別的表裡找不到對應的那一列,
掛不上去(這份是誰的子節?)
```

**真相**:那一格有兩份 record ——

```
record 0  p40  附註    total_col=114年12月31日  printed_total=373,868,040   8 列
record 1  p137 明細表  total_col=取得成本       printed_total=378,456,348   8 列
```

`378,456,348` 不是誰的子節點,它是**同樣 8 列的取得成本口徑**。
`core/closure.py:_tree()` 的模型是「一格所有 record 組成一棵樹,根 == 錨」,
它逐份找「我的印出合計等於別人的哪一列」,找不到就報錯 —— 但**跨口徑的 record
本來就不該掛在同一棵樹上**。

「兩個口徑」在這個 codebase 是一等概念(`wide` / `wide_cost`、`buckets.basis_of`、
`wide.pick(basis)`)—— **只有 ④ 不知道**。

**改法**:`_tree()` 分樹前先依口徑分組,一個口徑一棵樹,各自對自己的合計閉合。
判準用既有的 `buckets.basis_of(rec)` / `total_col in COST_COLS`,**不新寫一套口徑
判斷**(那正是這個 repo 反覆長 bug 的形狀)。

**踩到的 5 格**(改完必須全部轉綠,且其餘 198 格判斷不變):
```
202104_兆豐_個體|Trading   202304_中信_個體|OCI     202304_中信_個體|Trading
202304_富邦_個體|OCI       202504_華南_個體|OCI
```

**驗收(必須證明會失敗)**:把一份**同口徑**的子表合計改掉一塊錢 → ④ 必須仍然
報錯。只讓跨口徑那條路過,不是把 ④ 整個放寬。

## 洞② 撤銷人工裁示:網頁上做不到 ⚠️ 使用者的直接阻塞

```
core/webdata.revoke()   存在,且乾淨(git 可還原、帶 why/by 稽核)
server.py               0 個出口
web/workbench.js        0 個出口
```

帶 `_src` 的格,`file_cell()` 的 append-only 守衛擋下機器覆蓋(**那道守衛是對的,
不要動它**)。但沒有撤銷出口 = 人一旦裁示錯就永遠改不回來,只能開終端機。
`revoke()` 的 docstring 自己寫著「沒有撤銷口的話…那不是保護,是把自己鎖在門外」——
這支寫好了,只是沒接上去。

**實例**:`202402_富邦_個體|OCI`、`202502_富邦_個體|OCI` 現在存的是 2 列彙總,
而 v4 早就讀到 7~8 列明細,重抄永遠寫不進去,畫面只說「未歸檔」。

**改法**:
1. `server.py` 加 `POST /api/revoke` → `webdata.revoke(doc, cls, why, by)`
2. 文件頁的格卡片上,**只在該格 `human_ratified` 時**顯示「撤銷人工裁示」
3. 確認框要**列出將被丟掉的人工列**(沿用 `confirmOverwrite()` 已有的作法),
   並講明「撤銷後這格會變成『還沒抄』,git log 可還原」
4. `why` **必填** —— 撤銷是丟掉一個人的判斷,跟 `set_cellmeta` 同一個標準

⚠️ **不要讓重抄自動撤銷。** 那會讓守衛形同虛設 —— 守衛防的正是「機器無聲蓋掉
人工」,自動撤銷只是把無聲換個地方發生。

## 洞③ 「這格為什麼發不到分析頁」畫面上沒說 — 143 個單位

`build.py` **已經逐單位記了理由**,落在 `build_manifest.json`:

```
143 個 blanked 單位
  98  v3 該口徑為 null(該口徑在文件裡不存在或視圖不成立)
  23  v3 沒有這一格
  22  v3 該格檢查未通過
```

**這是純接線,不必新增任何判斷。** 複核台今天完全沒讀這個檔,所以使用者在
文件頁把一格編到差額 0、綠勾全亮,卻不知道它仍然發不出去、也不知道為什麼。
「已抄 99」與「發布單位 70」之間那道落差,畫面上沒有任何地方解釋。

**改法**:
1. `core/webdata` 讀 `build_manifest.json`,依 `facts_key` 索引出每格的
   發布狀態與理由(**只讀,不重算** —— 重算就是第二份實作)
2. 文件頁每個格卡片加一行:`發布:✓ 已發布` / `✗ 未發布 —— {reason}`
3. ⚠️ manifest 可能比 `facts/` 舊(就是那條「按重建才會發布」的紅字)。
   **舊了要明講**,不能拿舊理由當現況:比 mtime,舊就顯示
   「(這是上次重建時的結果,facts 已經更新)」

## 洞④ 同一格有兩套互不知道的檢查

- **v4 witness**(5 道)→ 決定 GREEN/RED → 決定能不能歸檔
- **v3 六道**(`transcribe.verify`)→ 只顯示,不擋歸檔

兩套對同一格各講各的。使用者截圖上同時出現「v4 判定可歸檔」與「六道 ④ 未過」,
兩句都對,但畫面沒說哪個管事,人只能猜。

**這一項最大,而且不該急著動。** 兩套檢查是歷史產物(v3 管線與 v4 管線並存),
收斂它等於決定「哪一套是真的」,那是架構決定不是接線。

**這一份只做一件事:讓畫面說清楚哪個管事。**
在格卡片上把兩組分開標題顯示 ——
`歸檔判準(v4)` 與 `品質檢查(v3,不擋歸檔)`,各自列自己的項目。
**真正的收斂留給 v11,並且要先回答「哪一套是真的」這個問題,不在這裡順手決定。**

## 順序

**② → ③ → ① → ④**

- **②** 最小,而且是使用者現在真的被卡住的地方(富邦兩格改不動)
- **③** 純接線,資料都在,做完「編輯完卻沒發布」這個困惑就消失
- **①** 5 格假警報,要動 `closure._tree()`,得小心不要放寬同口徑那條路
- **④** 只做標示,不做收斂

## 不做什麼

- **不動 `file_cell()` 的 append-only 守衛。** 洞②補的是撤銷出口,不是拆守衛。
- **不讓重抄自動撤銷人工裁示。**
- **不在洞③重算發布資格。** 只讀 `build_manifest.json`,理由由 `build.eligible()`
  一處產生。
- **不在洞④收斂兩套檢查。** 那要先決定哪一套是真的,是 v11 的事。
- **不放寬 ④ 的同口徑閉合。** 洞①只讓跨口徑不再被誤判成子節點。
