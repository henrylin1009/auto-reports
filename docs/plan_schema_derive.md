# Schema 重新設計 —— 只跟模型要它唯一能給的東西

**問題的起點是一句話**:「不都有 114 年?那還不知道是這格?」

對。`202502` = 民國 114 年 6 月 30 日,檔名就寫著。系統知道期別、知道錨值、
知道候選頁 —— 然後它**要模型告訴它哪一欄是本期**,模型答錯 6 次,每次讓整格死掉。
而正確答案系統算得出來,**213 份 record 全部唯一命中,零歧義**。

寫於 2026-07-30。所有數字都是當天實測,不是估計。

**現況(2026-07-30)**:D1 / D2 / D3 完成(見 §6)。D3 有兩處實作時跟原計畫
不同——`_taxonomy_gap` 不需要改(D1 已經解決根因)、`extract_v2` 只搬走
`fill_auto` 那條線的依賴(舊 v2 管線本身還有別的呼叫端,退場是另一個計畫的 R5)。
**D4(判斷點配證據,§5)尚未開始。**

## §0 實測 —— 失敗幾乎全在「系統自己知道的欄位」上

25 格拒收,逐格跑 `transcribe.verify()` 分類倒在哪一道(一格可能倒在多道):

| 倒在哪 | 幾格 | 這道在驗什麼 |
|---|---|---|
| **A 破折號列**(合計欄印 `—`) | **14** | schema 合規:規則說「印 `-` → 記 0」,模型沒照做 |
| **C `printed_totals` 逐欄對不上** | **14** | 一個**選填**欄位,填錯就整格死 |
| D 有列分不到桶 | 8 | **真的判斷問題** |
| B `printed_total` != 錨 | 3 | 模型抄錯一個系統已經知道的數字 |
| E 列相加 != `printed_total` | 1 | **唯一真正有資訊量的算術失敗** |

而模型在它**真正的工作**上幾乎不出錯(`plan_web_complete.md` 附錄實測):

```
facts/ 的金額   3,740 筆   錯 0
facts/ 的名字   1,602 筆   錯 14(全是認錯字,非虛構)
```

**閘門不是在擋「抄錯」,是在擋「schema 不合規」。**

### `total_col` 是可推導的 —— 213/213 唯一

| 語料 | 份 record | 「某一欄列和 == 錨」命中幾個欄 |
|---|---|---|
| `facts/` 已歸檔 | 185 | **全部剛好 1 個** |
| `work/rejected/` 被拒收 | 28 | 25 份剛好 1 個、3 份 0 個 |

0 個命中的那 3 份 = **真的抄錯了**。這才是有資訊量的失敗。
而模型在「唯一命中」的 25 份裡挑錯 6 次 —— 挑錯的答案系統本來就算得出來。

### 更荒謬的:`printed_total`

第 4 道檢查「`printed_total` == 錨」,而 [transcribe.py:112](../transcribe.py)
的 docstring **自己寫著**:

> ⚠️ 用錨值定位之後這道**定義上必然成立**(候選頁就是因為印著錨值才被選中),
> 所以它不是獨立檢查

系統要模型抄一個它已經知道的數字,再檢查抄得對不對,抄錯就殺掉整格。

## §1 根因 —— schema 把三種完全不同的欄位混為一談

今天 `fill.RULES` 跟模型要一份 record,裡面有:

| 欄位 | 這是什麼 | 誰該提供 |
|---|---|---|
| `rows[].name` / `cols` / `group` | **只有看得到那一頁的人/模型能給** | 模型 ✔ |
| `source_kind` | 同上(附註 or 明細表) | 模型 ✔ |
| `printed_totals` | 紙上印的逐欄合計 —— **獨立的第二來源** | 模型 ✔(見 §3 的但書) |
| `source_page` | ⚠️ **實作時修正**:只知道候選頁**集合**,不知道某一份 record 是哪一頁 | 模型(見下方修正說明) |
| `printed_total` | **系統已經知道**(就是錨) | 系統 |
| `total_col` | **系統推導得出來**(213/213 唯一) | 系統 |

**跟模型要它已經知道或推導得出來的東西,等於自己製造失敗模式。**
實測:25 格拒收裡有 22 格是這麼死的。

> ⚠️ **D2 實作時發現這張表原本把 `source_page` 也算成「系統已經知道」是錯的。**
> 抽樣 60 份 PDF 的候選頁分布:49/82 格有 **2 個以上**候選頁(`locate.pages`)。
> 「附註」與「明細表」兩份 record 常常落在不同候選頁,系統只知道候選頁集合,
> 不知道某一份 record 具體來自哪一頁 —— 這件事仍然只有讀得懂那幾頁的人/模型
> 能回答。實作時已修正,`source_page` **繼續跟模型要**,`docs` 與 `fill.RULES`
> 的 `DERIVED_FIELDS` 只列 `total_col`/`printed_total` 兩項。

### 副作用:路由也被污染了

`fill._taxonomy_gap` 判定「分類表缺口」的條件是**假裝把提案收錄之後整格會通過**
([fill.py:114](../fill.py))。所以只要同時有一個破折號列,分桶問題就被遮住 ——
那格不會進裁示台,而是掉進拒收堆。

實測:8 格有真的分桶問題,**一格都沒進裁示台**。把 schema 雜訊清掉之後,
2 格正確路由過去了(見 §2 的模擬結果)。

## §2 重新設計 —— 三層分開

```
抄列層(模型)    只給:{source_kind, rows:[{name, group, cols:{欄名:金額}}], printed_totals?}
                    ↓
推導層(系統,新) total_col     = 唯一使「列和 == 錨」成立的那一欄
                 printed_total = 錨(定義)
                 破折號列       = 缺合計欄的列補 0(**由錨確認過才補**)
                 對不上的 printed_totals → 丟掉,不是殺格
                    ↓
驗收層(六道)    只驗真正有資訊量的東西(見 §3)
```

**推導失敗的三種處置要分開**,這才是新的閘門:

| 命中幾個欄 | 意思 | 處置 |
|---|---|---|
| **0** | 真的抄錯了 | 拒收(今天 3 格,這才是真的) |
| **1** | 推導成功 | 直接用,不必問模型 |
| **≥2** | 歧義 | 送人裁示(今天 0 格,但要有出口) |

### 模擬結果(實跑,不是估計)

把推導層套到現有 25 格拒收上,再跑一次完整的 `transcribe.verify()` + `_taxonomy_gap`:

| | 幾格 |
|---|---|
| **推導後直接通過** | **17** |
| 路由到裁示台(分類表缺口,提案清單有了) | 2 |
| 推導失敗 = 真的抄錯(0 個欄命中) | 3 |
| 仍然拒收(第 5 道:兩層附註的小計列) | 3 |

**25 格卡住 → 只剩 6 格需要人看,而那 6 格是真的需要人看。**

## §3 誠實面對 —— 「驗收器拿去搜尋就不再是驗收器」

`plan_web_complete.md` 附錄有一條裁示過的教訓:

> 「錨對帳可以當抽取器,一道算術全包」→ 41% 是垃圾解。
> **驗收器拿去搜尋就不再是驗收器**

本計畫確實在用錨去搜尋,所以必須說清楚差別在哪、以及**哪一道真的被燒掉了**。

### 差別:搜尋空間差好幾個數量級

| | 當時被推翻的做法 | 本計畫 |
|---|---|---|
| 搜什麼 | **哪些列是資料列**(從候選網格挑組合) | **哪一欄是合計欄**(2–4 個已知欄名挑 1) |
| 空間 | 組合爆炸 | **≤4**,且實測 213/213 唯一 |
| rows 從哪來 | 演算法自己湊 | **模型抄好的,固定不動** |

湊組合會湊出垃圾解;在 4 個欄名裡挑一個不會。

### 但是:①②④ 確實變成恆真了

推導完 `total_col` 之後,「列和 == `printed_total`」與「`printed_total` == 錨」
**依定義成立**。這是真的損失,不能粉飾。

**不過那兩道今天驗到的東西本來就不是「數字對不對」**:
- ④ 的 docstring 自己說它「定義上必然成立」
- ①② 今天的 14 次失敗全是「有列缺合計欄」= schema 合規,不是算術

真正的算術檢查(**有沒有某一欄的列和 == 錨**)不但被保留,而且變成顯式的、
會失敗的閘門 —— 實測 28 份 record 裡有 3 份倒在它上面。

### 剩下有牙齒的是這三道

| 道 | 為什麼還有牙齒 | 實測倒了幾格 |
|---|---|---|
| **推導本身**(0 個欄命中) | 模型抄錯值 → 沒有任何欄湊得到錨 | 3 |
| **⑤ 列皆可分桶** | 擋兩層附註(玉山 2021H1 那個「四道全過、產出是廢的」洞) | 3 |
| **③ 雙表互對** | 擋名字/金額錯位 —— 算術驗不到配對 | — |
| **⑥ 逐欄合計** | ⚠️ **只在 `printed_totals` 是模型從紙上讀的時候才有牙齒** | — |

⚠️ **`printed_totals` 絕對不准改成系統自己算。** 算出來的話第 6 道就恆真了,
而它是明細表「取得成本」欄(成本口徑)唯一的驗證來源。它必須維持「模型獨立讀一次」。
改的只有**失敗時的處置**:丟掉那個 `printed_totals`(該格成本欄變 null,
誠實的「沒驗過就不上」),而不是連公允那欄一起殺掉。

### 每一道都要證明會失敗

照 `memory/checks-must-fail`,推導層上線同時要有注入測試:
把某一列的金額改掉 → 必須變成「0 個欄命中」;
偽造一個 `printed_totals` → 第 6 道必須抓到並丟棄那個欄。
**沒有注入測試的推導層 = 恆真閘門的新溫床。**

## §5 判斷點必須配證據 —— 12 個判斷點,只有 1 個做到

使用者 2026-07-30 裁示:

> 「我要做決定,右邊應該要有對應的資料讓我去確認。**都應該要是這樣。**」

這不是介面美化,是這整個工作台的**存在理由**。左邊問你一個判斷、右邊擺著
判斷依據 —— 兩者不在同一個畫面上,人就只能憑印象按,而憑印象按出來的裁示
跟沒有裁示一樣危險(這是 `plan_web_complete.md` §6② 對 `why` 必填的同一個論證,
只是換到證據這一邊)。

### 盤點(2026-07-30 逐個對照 [workbench.js](../web/workbench.js))

| 判斷點 | 這是什麼決定 | 右邊有證據? |
|---|---|---|
| 點已抄的列 | 核對一列 | ✅ **唯一做到的** —— 跳到 `rec.source_page` |
| ✎ 編輯一列 / × 刪一列 / + 新增列 | 改事實 | ❌ 表單開了,右邊不動 |
| 重抄 / 指定頁重抄 | 覆蓋整格 | ❌ |
| **選合計欄**(拒收面板) | 決定哪一欄是本期 | ❌ ← 使用者指的這個 |
| ✎ / × 拒收面板的列 | 改 / 刪 | ❌ |
| **「我看過原始頁,照這樣歸檔」** | **最重的裁示** | ❌ **按鈕上寫著「我看過原始頁」,而畫面完全不保證你看過** |
| 標記無資料 | 宣告這份文件真的沒有 | ❌ |
| 退回重抄 | 清標記重跑 | ❌ |
| 拖 chip 改桶(分桶頁) | **改全域規則**(`buckets.SYN`,影響所有文件) | ❌ 只有 tooltip 列 cell_key |
| 裁示台選桶 | **改全域規則** | ❌ 只有 `<details>` 列 cell_key 文字 |

**12 個判斷點,1 個有證據。而證據最少的兩個,恰好是唯二會改動全域規則的。**

### 順帶量到一個直接妨礙查證的 bug

同一張卡片上,紅字理由寫 **`@p35`**,卡片標題寫 **`p.36`** —— 同一頁,兩套頁碼。

`transcribe.verify()` 的 tag 是 `f"p{rec['source_page']}"`([transcribe.py:364](../transcribe.py)),
**0-based 直接印出來**;前端顯示一律 `+1`。而 [workbench.js](../web/workbench.js)
檔頭自己寫著:

> ⚠️ 頁碼一律 0-based……**畫面上顯示才 +1。不要在別的地方偷偷換算。**

錯誤訊息就是「畫面上顯示」的東西,漏了這條規矩。
**已確認可安全修**:`core/ingest.py` 與 `core/expand_policy.py` 用的是函式名
(`check_identity`…)當 key,沒有任何人 parse 這串顯示字。

### 設計 —— 一個統一的出口

```js
showEvidence({doc, page, why})   // 所有判斷點都只呼叫這一支
```

三條規矩:

1. **判斷點 = 證據點。** 任何要人下判斷的元件,渲染時就要知道自己的證據在哪一頁;
   給不出頁碼的判斷點,要在畫面上明講「這個判斷沒有頁級證據」,不准沉默
2. **重的裁示要先看過。** 「照這樣歸檔」「標記無資料」這類終局判斷,
   按下去之前右邊必須已經停在該格的來源頁(不是強制卷動到底那種假確認,
   而是**按鈕本身負責把證據叫出來**)
3. **跨文件的判斷要給證據清單。** 分桶 / 裁示台改的是全域規則,證據不是一頁而是
   多頁 —— 要列出「這個名字出現在哪幾格的哪一頁」,每一筆點得進去

### 後端要補的

`queue_view()` / `bucket_view()` 現在的 `cells` 是一串裸 cell_key
(`"202304_富邦_個體|AC"`),**沒有頁碼**,所以前端連想跳都跳不了。要升級成:

```json
{"cell_key": "...", "doc": "...", "cls": "AC", "page": 40, "name": "..."}
```

`page` 從 `facts/` 裡那一列所屬 record 的 `source_page` 取。
拒收面板則**純前端就能接** —— `rec.source_page` 早就在手上了。

### ② 「重的裁示按下去之前先跳頁」會不會太吵?
