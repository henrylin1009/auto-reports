### 為什麼 gemini 那批是最大的洞

實測 `202502_5836_AI3`（富邦 2025H1），同一份 PDF：

```
gemini   OCI 2 列,名字是「公允僵值」(PDF 裡沒有這個字),group=有僵證券
         source_page=38 → 那頁是金融負債,抓錯頁
         但 total = 189,286,620 —— 是對的

claude   OCI 7 列 page=39  total=printed_subtotal=bs_anchor=189,286,620
         上市櫃股票 28,510,269 / REITs 8,703,038 / 未上市 2,043,003 /
         政府公債 59,936,220 / 公司債 44,999,472 / 金融債券 39,404,486 / 其他 5,690,132
         21 列全部分得到桶,**零個新 SYN 條目**
         cost 正確填 null 並註明「半年報無重要會計項目明細表」
```

**關鍵**：gemini 的**總額是對的**，只是把 7 列明細抄成 2 列標題。
→ **只驗總額的閘門會放它過，然後網站印出一堆 0。**
救下這格的是「逐桶必須分得出來」那道要求。閘門設計是對的，
但這也說明 gemini 的錯誤型態是「總額對、明細錯」——最難靠總額察覺的那種。

已知含壞字的 4 格全部被閘門擋住、無一上網（`202402_5836|OCI`、`202502_5836|OCI`、
`202502_5836|Trading`、`202503_5841_AI1|Trading`）。這是閘門第一次有實測戰績。

## 順序的理由（只有一條原則，不再變）

**先讓地基可信，再往上疊。**

- ①（可信度）在 ⑤（覆蓋率）前面：補格子是往沒驗過的地基上加東西，
  而且地基若要重鋪，新格子還得再跑一次。
- ④（merge）夾在中間是因為它跟 ① 完全不相干，而且線上現在流通的是**更舊**的
  資料（7/24 的舊管線），先換掉純粹是改善，不需要等 ① 完成。

## 不做的事（明確排除，免得又飄回來）

- 不做保留集測驗。抽了兩次都沒抽中「沒看過的銀行」，而且 ① 的對照本身
  就是更強的證據（46 份文件雙抽取器逐桶比對，遠大於 3 份）。
  抽籤紀錄留在 `docs/holdout_20260810.md` 當歷史。
- 不做 2018–2019。見 ⑥。
- 不重寫架構。skill/程式的邊界已經對了：
  **LLM 只做「看得見就抄」（`/fill`、`v4/reader`），輸出凍結成 `facts/`；
  程式只做「判斷與發布」（`build.py`、分桶、閘門），純函數、可重跑。**
  分桶永遠不能是 skill，否則同一份文件跑兩次會得到不同的網站。
