# 網頁完備計畫 —— 讓每一種卡住的狀態都在瀏覽器裡有出路

**目標**:任何一格資料,不論管線把它留在什麼狀態,人都能**只用瀏覽器**把它處理完。
不回 chat、不開終端機、不手寫 JSON。

**明確不是目標**:提高自動化率。自動化是 `plan_pipeline.md` 的事(尚未寫),
本計畫**刻意先做完備性** —— 因為自動化到 80% 或 60% 都不影響「剩下的能不能收斂」,
而收斂能力才是決定這個專案能不能交付的東西。

**判準**(兩條,都可機械驗證):
1. §0 盤點表裡每一列都有一個對應的網頁動作
2. `python3 build.py --diff` 逐字不變 —— 加入人工出口**不准動到任何既有發布數字**

寫於 2026-07-30。基準線與量測全部是當天實測,不是估計。

### 那個「手動貼 JSON」不是後門
[workbench.js:497](../web/workbench.js) 的 textarea 走的是 `submit()` →

## §1 根因 —— 閘門保護了品質,同時擋掉了人工修復

`facts/` 唯一的寫入口是 `submit()` → `fill.cmd_submit` → **六道全過才寫**。
[server.py:186](../server.py) 自己寫著:

> 「**不准為了 UI 方便新增任何接受分支** —— 網站與 CLI 必須是同一道閘門。」

那條裁示是對的,不要動它。但它有一個沒被處理的後果:

**人工修復的本質就是「我看過原始頁面了,雖然算術對不上、桶認不出,但事實就是這樣」
—— 而這句話在系統裡沒有地方可以說。**

實例(2026-07-30 實測):玉山 110 年報 [p121 明細表](../pdf_cache/202104_玉山_個體.pdf)
的文字層是 `$ 12,216400`(千分位少一位)。用印出合計反推真值是 **12,216,100**,
文字層給的 12,216,400 差一位數字本身。這一格:

- 機器抄不對 —— 文字層就是錯的
- 六道會擋 —— 第 ⑥ 道差 300
- 人看得出來 —— 但沒有任何介面可以把 12,216,100 寫進去

## §2 概念 —— 人工裁示是一種合法的資料來源

不放寬閘門,而是**新增一種「人工權威」的來源,並讓它在資料裡看得出來**。

這在其他領域是解決過的問題,結構都一樣:

| 領域 | 做法 |
|---|---|
| 會計系統 | 手動調整分錄:可以改,但必須有理由、核准人、對應憑證。不是繞過控制,是換一種授權 |
| 臨床試驗資料(EDC) | query/response:系統質疑一個值 → 研究人員回覆並可覆寫 → 必須填 reason code → 該值**永久標記為已覆寫** |
| 資料平台 | manual override table + lineage 欄位,下游知道這個值是人寫的 |
| OSM / Wikipedia | 編輯即歸屬:誰、何時、為什麼,全部公開 |

本專案已經有這個模式的雛型:`_by`([fill.py:315](../fill.py))是稽核欄位,
`facts.py` 把它列為已知選填欄位,`wide` / `buckets` / `verify` **一律不准讀它**。
`_src` 是同一個模式再長一個。

### `_src` 的形狀

```json
{"name": "國外機構發行債券（註一）",
 "cols": {"帳 面 價 值": 12518061, "總 面 額": 12216100},
 "_src": {"by": "henrylin", "at": "2026-07-30T14:22",
          "why": "文字層缺一位千分位,用印出合計反推",
          "evidence": {"page": 121, "machine_said": 12216400}}}
```

### 三條規則

1. **沒有 `_src` = 機器抄的**(今天所有列)。有 `_src` = 人裁示的
2. **六道對人工列照跑、結果照記,但不阻止歸檔。** 不過就在網站上標黃,不是丟掉
3. **人工列在網站與 `data.json` 裡看得出來**(一個旗標)。稽核軌跡 = `git log`
   —— 與 `buckets.SYN` 同一套邏輯,`plan_simplify.md` §5 已裁示過

⚠️ **第一行程式是把 `_src` 登記成已知選填欄位。** `facts.validate` 有「未知欄位」
檢查,實測 `202302_玉山_個體|OCI` 就因為 `出現未知欄位 ['source_file']` 被退掉整格。

## §3 三批 —— 每批獨立可驗收,順序不可換

### W1 —— 只接已有的後端(半天,零新概念)

1. `POST /api/requeue` 接上前端:REJECT 的卡片加一顆「退回重抄」
2. `/api/rebucket` 加**批次**:裁示一個名字 → 套用到全部同名的列
   - 判準來自實測:138 筆只有 21 個不重複名字,前四名(政府債券 45 / 外匯換匯合約 14 /
     受益證券 13 / 透過…工具投資 15)佔 63%
3. 裁示台雛形 `#/queue`:`pending_entries()` 排序後一屏一案,鍵盤 `1-9` 選桶、
   `空白` 跳過

**不動**:schema、`facts/` 寫入口、抽取管線。
**驗收**:`build.py --diff` 逐字不變;138 筆能在 21 次操作內清空。

### W2 —— `_src` + 可編輯列(一天,核心)

1. `facts.py` 把 `_src` 列為已知選填欄位(+ 測試:注入一個 `_src` 確認不被退)
2. `POST /api/row` —— 改 / 增 / 刪一列。必填 `why`,自動帶 `by` / `at` / `page`
3. `viewDoc` 左欄的每一列變成可編輯:名字、金額、group。右欄的來源頁渲染器**完全不動**
4. 六道結果改成**顯示**而非**阻擋**:人工列不過就標黃並列出哪一道不過

**驗收**:
- 玉山 `202104_玉山_個體|AC` 的 12,216,100 能在網頁上寫進去並歸檔
- 14 列亂碼能在網頁上改成正確名字
- 純機器格子的 `build.py --diff` 仍逐字不變(人工列是新增,不是覆寫)

### W3 —— cell 層 metadata(半天)

1. `POST /api/cellmeta` —— 三種裁示走同一支:
   - **手填錨**:解掉 98 格 `na`(96 錨讀不到 + 2 無候選頁,全部 ≤2022)
   - **標記「文件真的沒有這個資料」**:與「還沒抄」在畫面上必須分得開
   - **口徑裁示**(帳面 / 成本):附上那一行算術證據(有評價調整列 → 成本)
2. `POST /api/refill` —— 手動指定來源頁重抄,解掉「抄到彙總層」那 15 筆

**驗收**:§0 盤點表十列全綠。

## §5 閘門 —— 怎麼證明沒弄壞東西

沿用 `plan_simplify.md` §2 的 `check.sh`,加一道:

```
1. python3 build.py --diff              → 逐字不變(27s)。最強的一道
2. 逐支跑 test_*.py                     → 今天綠的維持綠
3. python3 locate.py --expand           → 11 格定位回歸
4. server 煙霧測試                       → 新增的四支端點各打一次,存 JSON 快照
5. **注入測試**                          → 依 memory/checks-must-fail:
     寫一個帶 _src 的假列進 facts/,確認 ①「六道結果照記」真的記到了
     ②「人工列標黃」真的黃了 ③ wide / data.json 沒有把它當機器列
```

第 5 道是必要的。實測教訓:恆真閘門看起來全綠,注入錯誤才知道它有沒有在做事。

## §6 需要你裁示的三件事

① **人工列要不要進 `data.json`?**
   傾向:要,但帶旗標,前台可以選擇顯示或隱藏。理由:不進的話「網頁上 100% 可解」
   只解到 `facts/`,沒解到產出。

② **`_src.why` 要不要強制填?**
   傾向:要。它是這整個機制唯一的品質控制 —— 沒有理由的覆寫跟沒有覆寫一樣危險。
   代價是每次多打一行字。

③ **≤2022 那 96 格錨讀不到的,要不要做?**
   `webdata.CUTOFF_YEAR = 2023` 已經把它們排除在畫面外。W3 的「手填錨」讓它們**變得可做**,
   但要不要真的去做是另一件事。**這件事不擋 W1~W3。**
